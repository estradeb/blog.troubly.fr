PAC (Privilege Attribute Certificate)

  • The PAC is part of the Kerberos tickets TGT and TGS in the “authorization_data” section (it can be found in a AS_REP, TGS_REP and AP_REQ)
  • The PAC is a data structure used to transport authorization information of a Principal: SID of the domain, RID of the user, RID of its membership groups, credential information , etc.
  • This structure, initially designed and used by NETLOGON is now also used in Kerberos tickets
  • Upon decryption of the TGS by the service, the PAC is accessible to the service and group membership can be freely used for application permission Exemple of a PAC in a user’s TGT : ![[Pasted image 20250206165307.png]]

Security descriptor

  • Contain the security information that protects a securable object
  • One is assigned to each AD Objects
  • Contains DACL (discretionary access control list)
    • identifies the users and groups allowed or denied access to the object
    • is a collection of ACE (Access Control Entries) - Each ACE grants or denies a set of access rights to the object

Kerberos SSP secrets

Ekeys

Ekeys are an alternate form of the users password. Ekeys are stored by LSASS in various encryption format depending on local computer configuration and Windows version.

  • Ekeys are used for the timestamp encryption in AS_REQ.
  • It is also used by the KDC in AS_REP before a proper session key can be found.

With FAST, Ekeys are mixed up with the computer’s session key (getting the “armor key”) to be used in similar steps (AS_REQ/AS_REP)

Ticket Granting Ticket

The Ticket Granting Ticket is computed by the KDC for an authenticating client account.

  • It is encrypted by the krbtgt’s secret so only a domain controller can decrypt it.
  • It contains a copy of the session key, an expiration date, the account’s informations and PAC

Session Key

The session key is a temporary symmetric encryption key computed by the KDC. Its included within the AS_REP in two locations :

  1. Into the user’s TGT (which the authenticating account cannot decrypt)
  2. Into the [enc-part] (which the authenticating account can decrypt) All future communications with the KDC are encrypted with the session key

Armor Key & Challenge Key

In armored kerberos, the Armor key and the Challenge key are new keys derived from a combination of existing keys from the computer and user account eKeys. The function KRB-FX-CF2() combine two keys based on the pseudo-random function defined in RFC3961

Armor_key = KRB-FX-CF2(computer's subkey, computer's session key)

Challenge_key = KRB-FX-CF2(armor_key, user's eKeys)

[!Warning] Oversimplification This is a simplified version of the computation used. Please refer to rfc6113 to get a more precise understanding
